二、应用流量统计

2.1 Bridge 应用：读取 Linux 网桥累计计数

Bridge driver 枚举当前网络命名空间中的 lzc-br-* 网桥，并读取：

/sys/class/net/<bridge>/statistics/rx_bytes
/sys/class/net/<bridge>/statistics/tx_bytes
/sys/class/net/<bridge>/statistics/rx_packets
/sys/class/net/<bridge>/statistics/tx_packets
/sys/class/net/<bridge>/statistics/rx_errors
/sys/class/net/<bridge>/statistics/tx_errors
/sys/class/net/<bridge>/statistics/rx_dropped
/sys/class/net/<bridge>/statistics/tx_dropped

Docker socket 只负责把网桥、Compose project、应用 ID、容器数量和标题关联起来，不提供流量计数。网桥计数是内核累计值，网桥被删除或重建后会归零。

在当前应用语义中，网桥 rx_bytes 被作为应用上传计数，tx_bytes 被作为应用下载计数：

应用容器产生网络包
lzc-br-*网桥累计计数
Netwatch读取 sysfs
应用 ID聚合展示

2.2 Host 应用：按容器 cgroup 统计

Host driver 不能从 lzc-br-* 计数中得到 Host 容器自己的流量，因此代码创建两个 cgroup_skb eBPF 程序：

  • ingress 程序写入 RX map；egress 程序写入 TX map。
  • map 的 key 是 cgroup ID，value 是字节数和包数。
  • 程序首次读取 Host 容器时附着到该容器 cgroup，之后按 map 读取累计值。
  • collector 为每个 Host 容器输出独立计数记录，不在读取阶段提前按应用求和；状态层按 cgroup 路径维护独立 baseline 后再聚合。
  • 两个计数 map 优先 pin 到宿主机 bpffs 的 netwatch/ 目录；Netwatch 重启后会重新加载同一 map，内核累计计数可继续使用。程序和 cgroup attachment 仍由当前进程管理，服务退出后会自动解除。
  • attachment 同时记录 cgroup 路径和 ID；完整运行时清单确认容器停止、路径被新 cgroup 复用或 map key 已无活动归属后，关闭旧 link 并删除 RX/TX key。清单不完整时跳过整轮清理，避免误删。

cgroup 路径按以下顺序解析并验证：Docker inspect 字段、宿主机 /host/proc/<PID>/cgroup、懒猫 systemd cgroup 结构。若加载、附着或读取失败，快照应携带具体诊断。

当前状态：Host eBPF 依赖宿主机 cgroup v2、容器 PID/挂载、BPF 权限和内核支持。任何一项不满足都会导致 Host 统计不可用，但不影响 Bridge 统计。未挂载 bpffs、bpffs 不可写或 pin 失败时，统计仍会使用临时 map，并在 diagnostic 中明确提示重启会重置计数。目标懒猫盒子的 /sys/fs/bpf 当前是普通 sysfs 目录而非 bpffs，真机已验证会走这条降级路径。Host 统计不是 Docker 网桥统计的“另一份数据”，两者来源不同。

2.3 采样、速率和历史

  • 采样目标间隔约 2 秒；重复调用在半个采样间隔内会被跳过。
  • 每个独立内核计数源保存上一次计数作为 baseline：Bridge 使用网桥名，Host 使用容器 cgroup 路径。只累加正向差值；网桥/cgroup 重建或计数回退时只重建对应来源的 baseline。
  • 同一应用的多个网桥、多个容器按 app_id 聚合。
  • 实时速率 = 本次正向字节差 / 两次采样间隔，单位为 B/s；没有有效间隔时速率为 0。
  • 今日、本月流量按每日记录汇总；应用级历史和 baseline 持久化到 app_traffic_history.json。
  • 应用列表只展示当前仍有运行容器的应用，删除或停止的应用不会继续作为活动条目展示。

三、限制网速

3.1 当前支持范围

纯 Bridge 应用沿用网桥 TBF/police。实验开关开启时，Host 和 Mixed 应用使用物理默认出口上的应用级 TC 分类器；Mixed 只执行一次共享 limiter，不再给 Bridge 单独配置第二份额度。统一 Controller 仍要求所有活动目标能力检查和内核操作成功后才保存应用级限速状态。

3.2 Bridge driver 的 tc 执行位置

方向规则作用
下载网桥 root qdisc：tbf，固定句柄 194:限制网桥发出的流量；rate 使用用户输入的 Kbit/s，burst 按约 100ms 计算，latency 为 50ms。
上传网桥 ingress clsact 下的 matchall + police对进入网桥的流量执行限速；Netwatch 保留优先级 49152。
局域网例外优先级 49140 至 49144 的 flower pass 规则让 RFC1918、IPv6 ULA 和链路本地地址不受上传公网限速规则影响。

tc 命令来自宿主机，而不是 scratch 镜像内部：Netwatch 通过 nsenter -t 1 -m -n -r 进入宿主机的 mount/network namespace，并调用宿主机上的 tc。

安全边界：下载限速会替换网桥 root qdisc，因此检测到非 Netwatch 管理的 root qdisc 时会拒绝操作，避免覆盖其他网络组件。

3.3 Host/Mixed driver

阶段规则作用
Host socket 标记应用父 slice 上的 cgroup/sock_create + socket-local-storage同时附着懒猫 system slice 和顶层 exec slice；同一应用的多个 Host 容器共享实例。
下载分类默认物理出口 ingress 的 TC eBPFHost 通过 socket lookup 归属；Bridge 通过 egress 建立的 NAT 反向流归属；匹配后进入每应用共享 token bucket。
上传分类默认物理出口 egress 的 TC eBPF匹配 Host socket 或应用 Bridge ingress ifindex 后，只写入掩码 0x0fff0000 内的应用 mark。
上传限速fw + act_police + skbedit每应用一条共享 police，正常包继续并清除保留 mark，超限包丢弃；避免 GSO 下的 eBPF 重复计费。

Host/Mixed filter 使用优先级 49160/49161，只添加 clsact，不会替换物理网卡原有 root qdisc。IPv4/IPv6 的 TCP/UDP 共用该路径；RFC1918、loopback、link-local 和 IPv6 ULA 不进入公网预算。下载和上传都是 policing，不是无丢包 shaping：TCP 会通过重传近似收敛，UDP 超限包会直接丢弃。

拓扑边界：当前只选择一个默认出口；IPv4/IPv6 默认路由位于不同设备时拒绝启用。多 WAN、策略路由、VPN/tunnel、IPv6 扩展头和运行中出口切换尚未覆盖。

3.4 修改、取消和恢复

  • 限速值只有在所有活动目标的内核操作成功后才写入持久化状态。
  • Mixed 应用只调用一次 Host/Mixed limiter；修改速率时原子更新应用 generation，并替换同一条上传 police。
  • 取消限速时删除应用 filter、cgroup attachment 和 map；不存在的规则被视为已清理。纯 Bridge 同时删除 root TBF 和上传 filter。
  • 后台每约 2 秒 reconcile 一次持久化限速，并与手动限速操作串行化，避免取消操作被旧状态重新覆盖。
  • 限速器区分三种状态：持久化的 desired、最近一次 tc 接受的 applied、实际核验结果 in_sync。内存中的 applied 只用于回滚，不能证明内核规则仍然存在。
  • 周期核验 root TBF、BPF/filter、police 速率与动作；规则缺失、速率不一致、网桥/cgroup 重建或 Netwatch 重启时会自动恢复。
  • 联合修改限速和外网策略时，即使最后保存 BlockedApps 失败，也会恢复防火墙、内存禁网状态、内核限速和磁盘限速；任何回滚失败会与原始错误一起返回。

四、禁用外网

4.1 Bridge driver

Bridge driver 使用宿主机 Netwatch 自有双缓冲 chain，并由 FORWARD 链跳转到当前活动 chain：

-I FORWARD -i lzc-br-<id> -j DROP
-I FORWARD -i lzc-br-<id> -d 10.0.0.0/8 -j ACCEPT
-I FORWARD -i lzc-br-<id> -d 172.16.0.0/12 -j ACCEPT
-I FORWARD -i lzc-br-<id> -d 192.168.0.0/16 -j ACCEPT

IPv6 同样允许 fc00::/7 和 fe80::/10，其余转发流量丢弃。由于每次插入 ACCEPT 都放在链首，局域网例外会先于 catch-all DROP 生效。

规则写入宿主机的 Netwatch 自有双缓冲 chain，并由 FORWARD 链跳转到当前活动 chain。iptables 操作失败时不再删除容器默认路由，避免无法可靠恢复的隐式断网。

4.2 Host cgroup driver

Host 模式没有独立网桥，代码使用 iptables 的 cgroup match，在宿主机 OUTPUT 链按应用 cgroup 路径匹配：

-I OUTPUT -m cgroup --path <app-cgroup-path> -j DROP
-I OUTPUT -m cgroup --path <app-cgroup-path> -d 10.0.0.0/8 -j ACCEPT
...（其余私有网段、IPv6 本地网段）

Host 模式只支持“禁用外网”，不支持“禁用全部网络”；使用 Netwatch 自有 NETWATCH-OUT-A/B chain，在 OUTPUT 链按应用 cgroup 路径匹配。Host 控制使用的是应用级 cgroup 父 slice，因此同一应用的多个 Host 容器会一起受到控制。懒猫中容器主进程位于 system.slice/runc-lzc-os.scope/lzcapp.slice/...，而 lzc-docker exec 进程位于顶层 lzcapp.slice/...；实现会在第二棵 app slice 真实存在时同时生成规则，避免管理员 exec shell 绕过禁网策略。

4.3 状态保存与实验开关

  • 禁用状态权威保存在 BlockedApps，key 是 app_id；旧版本的 BlockedBridges 目标 ID 只作为迁移来源。
  • Host 控制要求“Host 网络控制（实验性）”开启；关闭开关时会清理 Host cgroup iptables 规则、Host/Mixed TC 限速及对应持久化控制状态。
  • 白名单系统应用不能执行禁用外网、限速或设置代理。
  • Controller 负责策略事务和失败回滚；防火墙 driver 使用 Netwatch 自有双缓冲 chain，在应用生命周期、服务启动和周期 reconcile 时重建规则。网桥重建后会按 app_id 把禁网策略重新展开到新目标。
  • 宿主机 iptables 可能是指向 /etc/alternatives/ 的绝对符号链接；能力检测不在容器根中跟随该链接，实际命令由 nsenter -r 在宿主根解析。
  • xt_cgroup --path 相对调用者的 cgroup namespace 解析；防火墙命令必须通过 nsenter -C 同时进入 PID 1 的 cgroup namespace，否则 nft 后端会以 RULE_APPEND ... Invalid argument 拒绝 Host 规则。

五、设置应用代理

5.1 配置与状态

  • app_proxy 是新应用弹窗的默认值；app_proxy_configs 按 app_id 保存每个应用自己的 HTTP/SOCKS5、IP 和端口，proxy_apps 只记录启用状态。
  • 恢复直连只关闭该应用代理并清理规则，保留其上次配置；修改默认值不会热切换已配置应用。
  • 旧版已启用应用如果没有独立配置，加载时自动复制当时的全局默认值。

5.2 数据路径与事务

每个启用代理的应用拥有独立 appProxyAdapter 和动态本地端口。Bridge 目标在 PREROUTING/FORWARD 按网桥匹配，Host 目标在 OUTPUT 按两棵应用父 slice 匹配；公网流量经 Netwatch 自有双缓冲 NAT/filter chain 重定向到对应适配器，局域网流量保持直连。

  • HTTP 上游转发 TCP；公网 UDP 和其他未支持协议失败关闭。SOCKS5 上游转发 TCP 和 UDP。
  • 代理地址是宿主机自身地址时优先拨号 loopback，失败再回退用户填写的地址；远程代理仍只连接原地址。宿主 DHCP 地址变化后，新应用默认值会刷新，但已配置应用保持各自地址。
  • nftables 兼容层未返回 UDP 原始目的地址时，从当前 network namespace 的 nf_conntrack 恢复 original/reply tuple；回包通过 IP_PKTINFO / IPV6_PKTINFO 使用反向 NAT 期望的源地址。仅本地重定向且首查未命中时执行最多 4 次、间隔 3ms 的有限重试。
  • “启用”通过一次 app-policy 请求原子提交应用配置和启用状态。修改应用 A 时先启动新适配器并切换规则，成功后才关闭旧适配器，不影响应用 B。
  • 禁用外网优先于代理；已配置代理的应用被禁网时状态为 paused，公网流量直接丢弃，恢复外网后代理规则自动恢复。
当前边界：上游只接受 IPv4/IPv6 地址和无认证 HTTP/SOCKS5。Host/Mixed 应用不能同时启用代理和限速；纯 Bridge 应用不受此互斥限制。

app-policy 使用字段级更新语义：未提交的限速、外网或代理字段不会被修改。应用包含多个目标时，Controller 先完成能力检查，再逐目标执行；任一目标失败会按相反顺序回滚已执行目标。只有内核操作和状态保存都成功才提交；最后一步保存失败时同样恢复防火墙、代理适配器、内存状态、内核限速和磁盘状态。快照中的 network_policy.limit_in_sync、internet_in_sync、proxy_in_sync 和 diagnostic 表示最近一次内核核验结果，不能用持久化期望值替代。

前端的“应用流量实时刷新”只影响页面是否显示并刷新实时速率列，不改变后台采样器；后台生命周期观察器仍会定期采样并维护历史、限速 reconcile。

七、已知限制与排障重点

  • 禁网状态不一致：先看 network_policy.internet_in_sync 和目标 diagnostic，再检查 Netwatch 自有 chain 是否存在；不要只看持久化的期望状态。
  • 限速状态不一致：先看 network_policy.limit_in_sync；limit_state=drifted 表示期望限速仍在，但实际 qdisc/filter 缺失或速率不一致。后台会自动修复，连续失败时 diagnostic 保留最近错误。
  • 代理状态不一致：先看 network_policy.proxy_state、proxy_in_sync 和 diagnostic；再检查该应用独立适配器及 Netwatch 自有 NAT/filter chain，不要只看 proxy_enabled。
  • HTTP 应用的 UDP 不通：这是当前协议边界，HTTP 上游只转发 TCP，剩余公网流量失败关闭；需要 UDP 时选择 SOCKS5。
  • Host/Mixed 代理与限速：两者当前互斥，必须先恢复直连或取消限速。代理按应用独立配置和监听，不共用上游或内部端口。
  • Host 统计不可用：先看快照中的具体 diagnostic，确认 cgroup v2、宿主机 proc/cgroup 挂载、BPF capability、程序加载和附着错误。Host 统计按每个容器 cgroup 独立读取和维护 baseline，再按 app_id 聚合；一个 cgroup 重启归零不会重置同应用其他容器的增量。
  • 限速后应用断网：检查网桥 ingress police 的动作顺序必须是 conform-exceed drop/ok；正常包应放行，超限包才丢弃。
  • 取消后仍受限：纯 Bridge 检查 root TBF 194: 和优先级 49140-49144/49152；Host/Mixed 检查默认出口优先级 49160/49161。同时确认后台 reconcile 没有重新读取旧的持久化状态。
  • 网桥统计不是应用精确进程统计：Bridge 模式下它统计的是整个应用网桥的内核计数；同一 Compose project 的多个容器可能汇总到一个应用。
  • Host 与 Bridge 混合应用：统计仍按容器 cgroup 和网桥分别采样后聚合；禁用外网分别调用 Bridge/Host driver，限速则只调用一次 Host/Mixed limiter，让两类公网流量共享应用预算。
  • 重启影响：Bridge sysfs 计数由内核维护，网桥重建会归零；Host eBPF map 只在真实 bpffs 可用时跨服务重启复用。由于 cgroup attachment 由进程管理，Netwatch 完全停止期间不会产生新的 Host 统计。目标盒子当前没有挂载 bpffs，真机重启验证确认临时 map 会归零，diagnostic 会明确提示。

八、Host/Mixed 限速验证结论

直接附着应用父 slice 的第一版 cgroup_skb token bucket 已被淘汰：该 hook 在 GRO/GSO 下的 skb.len 与应用实际接收字节不稳定对应，且 verifier 禁止读取 wire_len/gso_segs 修正。正式实现改为在物理默认出口分类和 policing：

组件职责共享语义
cgroup/sock_create给 Host socket 写入应用实例自己的 socket-local-storage。应用两棵父 slice 和多个 Host 容器共用同一实例。
TC ingress eBPFsocket lookup 识别 Host 下载，反向 flow map 识别 Bridge 下载，并执行 token bucket。Host 与 Bridge 共用一个下载 bucket。
TC egress eBPF按 socket tag 或 Bridge ifindex 分类，只写应用 mark。不在 BPF 内做 GSO 上传计费。
fw + act_police按应用 mark 执行原生上传 policing，随后只清理保留 mark 位。Host 与 Bridge 共用一条上传 police。

Linux 6.5 真机上，正式产品路径的 1 Mbps 单流结果为 Host 下载约 991 Kbit/s、Bridge 下载约 983 Kbit/s、Host 上传约 971 Kbit/s、Bridge 上传约 995 Kbit/s；Mixed 并发上传聚合约 998 Kbit/s。2 Mbps 热更新、filter 漂移自愈、Netwatch 重启恢复、清零和无残留清理均已验证，物理网卡原有 mq + fq_codel root qdisc 始终保留。

当前产品边界：

  • 这是 policing，不是 shaping；TCP 依靠拥塞控制收敛，UDP 超限包直接丢弃，128 KiB burst 会影响短流瞬时值。
  • 只支持 IPv4/IPv6 默认路由位于同一设备；多 WAN、策略路由、VPN/tunnel 和出口切换未覆盖。
  • IPv4/IPv6 的直接 TCP/UDP 已实现；IPv6 扩展头链尚未解析。
  • 每应用占用一个 mark slot，最多同时 4095 个 Host/Mixed 限速应用。
  • 空 clsact 可以在取消后保留；它不会替换或改变 root qdisc。
结论：Host/Mixed 限速已作为实验能力开放；UI/API 只有在实验开关、cgroup v2、默认出口和 TC/eBPF 条件都满足时才返回可用。bpffs 只影响 Host 统计 map 的跨重启累计，不是该限速方案的前置条件。
