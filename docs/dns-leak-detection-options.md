# DNS 泄露检测方案记录

> 当前结论：暂不实现。优先保留轻量、本地可运行、无需自建公网基础设施的方案。

## 背景与判断边界

DNS 泄露检测要回答的是：当前系统发出的 DNS 查询，实际由哪些递归解析器处理，以及这些解析器是否绕过了用户期望的 VPN、代理或指定 DNS。

单独读取 `/etc/resolv.conf` 只能说明配置，不能证明真实链路。单独依赖公网检测服务又会引入第三方可用性、隐私和网络连通性问题。因此后续应采用多来源交叉判断，并明确标注“系统配置”和“实际观测”的区别。

## 方案 A：自建权威 DNS 观测服务

参考 dnsleaktest.com、ipleak.net、BrowserLeaks 的模式：为每次检测生成唯一域名，客户端发起多次查询，由自建权威 DNS 记录实际访问的递归解析器 IP，再通过 ASN/地理信息归类。

外置条件：公网域名、NS 委派和 glue 记录；允许 UDP/TCP 53 入站的 VPS；权威 DNS、结果 API、任务存储和清理策略；ASN/地理信息来源；以及 DNS 传播、IPv4/IPv6、运营商拦截和防火墙的长期运维。

优点是观测链路完整、结果可控；缺点是基础设施和运维成本明显偏高，不适合当前项目第一版。

## 方案 B：调用成熟公共检测服务

参考 bash.ws/dnsleak、macvk/dnsleaktest：客户端生成随机查询并调用公共服务的结果 API，服务端返回观察到的解析器 IP，客户端再与出口 IP 的 ASN 进行比对。

优点是开发量小、检测模型成熟；缺点是依赖第三方、结果和隐私受外部服务影响，公共服务故障时无法检测。适合作为可选的公网验证模式，不应作为唯一结论来源。

## 方案 C：本地配置审计 + 公共 whoami 探针

推荐作为 Netwatch 的第一阶段方案。读取 `/etc/resolv.conf`、systemd-resolved 的 stub/link 配置和可获取的 DHCP/VPN DNS；同时使用系统解析器查询多个稳定的 resolver identity 域名，例如 Akamai `whoami.akamai.net`、`whoami.ipv4.akahelp.net` 和 Google 的 `o-o.myaddr.l.google.com` TXT 记录。

判定时区分配置 DNS、实际解析器、出口 ASN 和本机观测流量。建议执行 6～12 次、使用不同查询名、去重并设置总超时；首次查询和强制刷新都做双批次交叉验证，避免缓存或单次失败造成误报。结果应输出解析器列表、ASN/组织、配置与实际观测的匹配关系，以及“无明显泄露 / 疑似泄露 / 无法判断”和置信度。

局限是应用自行使用 DoH/DoT、浏览器独立 DNS、代理端解析等场景可能绕过系统解析器，不能承诺对所有应用可见。IPv6 DNS 也应单独检测，不能因为 IPv4 正常就判定整体正常。

## 方案 D：纯被动观测

只读取本地 DNS 配置并观察现有 DNS 流量，隐私和依赖性最好，但无法确认解析器身份，也无法发现缓存、DoH 或没有产生 DNS 请求的场景，只适合作为辅助信息。

## 建议落地顺序

1. 先实现方案 C，作为默认检测，结果以证据来源分栏展示。
2. 增加方案 D 的流量辅助观测，避免把端口号直接当成解析器结论。
3. 后续按需增加方案 B 的手动公网验证，并把第三方结果单独标注。
4. 暂不建设方案 A，除非项目需要独立、可审计的公网检测基础设施。

## 隐私与失败处理

检测域名、时间、解析器 IP 和出口信息都可能构成网络元数据。默认不持久化完整历史，不上传本地配置；第三方检测必须由用户主动触发。任何单一数据源超时、无 IPv6 或 ASN 查询失败，都应降级为“证据不足”，不能直接判定泄露。
