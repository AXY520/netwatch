Netwatch 0.10.1 · Architecture Note

应用限速、禁用外网与设置代理的技术原理

这三项功能共用一套“应用身份 → 内核控制目标 → 原子策略”控制面，但会根据 Bridge、Host 或 Mixed 网络拓扑选择不同的 Linux 数据面。本文说明数据包实际经过哪些 hook、状态如何提交，以及失败时如何回滚和自愈。

一、统一控制模型

发现Docker socket 与懒猫包元数据找到应用、容器和网络模式。
定位实例app_id 表示应用，instance_id 表示具体用户实例。
生成目标Bridge 绑定 lzc-br-*，Host 绑定应用父 cgroup。
能力预检检查 tc、iptables、cgroup v2、eBPF 和实验开关。
提交策略执行内核操作，全部成功后才保存期望状态。

核心抽象是 AppNetworkTarget 和 AppNetworkPolicy。前者回答“这个应用应该在哪个内核位置被识别”，后者只表达“上传/下载上限、是否允许外网、是否启用代理”。这样 API 和前端不需要理解 tc 句柄、cgroup 路径或 iptables chain。

宿主执行边界：Netwatch 自身是 scratch 镜像，不依赖容器内的 tc/iptables。Bridge tc 和防火墙命令通过 nsenter 进入 PID 1 的 mount/network/root；涉及 xt_cgroup --path 时还必须加入宿主 cgroup namespace。Netwatch 以 host network 运行，Host/Mixed 的 netlink 和 TC eBPF 直接作用在宿主网络命名空间。

二、限制网速

2.1 Bridge：在应用网桥上整形与 policing

下载网桥向容器发包，所以在网桥 root 使用 tbf。Netwatch 保留句柄 194:，设置 rate、约 100ms burst 和 50ms latency。
上传容器发出的包进入网桥 ingress，在 clsact 上用 matchall + act_police，超限包直接丢弃。
局域网例外上传方向先用 flower pass 放行 RFC1918、IPv6 ULA 和 link-local，之后才进入公网 police。
download: tc qdisc replace dev lzc-br-* root handle 194: tbf rate ... burst ... latency 50ms
upload:   tc filter add dev lzc-br-* ingress pref 49152 matchall \
          action police rate ... burst >=128KiB mtu 65535 conform-exceed drop/pipe \
          action gact pass

上传 police 后面的 gact pass 不只是放行动作，它的 action statistics 还用来统计真正通过限速器的字节。这避免把被 police 丢弃的发送尝试误显示为实际上传。为兼容 GSO 大包，burst 至少 128 KiB，MTU 为 65535。

保护其他网络组件：下载 TBF 需要占用 root qdisc。如果已经存在不属于 Netwatch 的 root qdisc，系统会拒绝限速，不会直接覆盖。

2.2 Host/Mixed：先识别应用，再在物理出口限速

  1. 在应用父 slice 附着 cgroup/sock_create，把应用 tag 写入 socket-local-storage。容器主进程树与 lzc-docker exec 树都会覆盖。
  2. 在 IPv4/IPv6 默认路由的物理设备添加 clsact，保留原有 root qdisc。
  3. TC ingress eBPF 通过 socket lookup 识别 Host 下载，通过反向 flow map 识别 Mixed 中 Bridge 的下载，然后在每应用 token bucket 中扣减字节。
  4. TC egress eBPF 通过 socket tag 或 Bridge ifindex 识别上传，只在 skb->mark 的 0x0fff0000 保留位写入应用 slot。
  5. 后续 fw + act_police 根据 mark 执行上传 policing，通过包继续并清掉保留 mark，超限包丢弃。

Mixed 应用不会再为 Bridge 目标安装第二套 TBF/police。Host 与 Bridge 都进入同一应用 generation、同一下载 bucket 和同一上传 police，因此用户设置的是应用总预算，不是“每容器各一份”。

本质是 policing：Host/Mixed 的上传和下载都会丢弃超额包。TCP 通过重传和拥塞控制逐步收敛到目标速率；UDP 超限包不会缓冲，而是直接丢失。

三、禁用外网

“禁用外网”不是删除容器默认路由，而是在宿主防火墙中实现“私网返回原链、其他目的地丢弃”。因此应用仍可以访问同机、局域网和懒猫内部服务，但无法访问公网。

目标iptables hook匹配条件放行范围最终动作
Bridgefilter/FORWARD-i lzc-br-*RFC1918；IPv6 ULA/link-localDROP
Hostfilter/OUTPUT-m cgroup --path ...再加 loopback 和 IPv4 link-localDROP
 
Bridge: -i lzc-br-* -d 192.168.0.0/16 -j RETURN
        -i lzc-br-*                     -j DROP

Host:   -m cgroup --path <app-slice> -d 192.168.0.0/16 -j RETURN
        -m cgroup --path <app-slice>                      -j DROP

3.1 为什么使用 A/B 双缓冲 chain

IPv4 和 IPv6 各自维护 NETWATCH-FWD-A/B 与 NETWATCH-OUT-A/B。更新时先完整写入非活动 chain，再把 FORWARD/OUTPUT 顶部跳转切到新 chain，最后清理旧 chain。这个过程避免在逐条更新时短暂放行公网，也为 IPv6 失败时恢复 IPv4 旧策略提供了回滚点。

3.2 两棵 cgroup 树

懒猫容器主进程通常位于 system.slice/runc-lzc-os.scope/lzcapp.slice/...，而 lzc-docker exec 创建的进程可能位于顶层 lzcapp.slice/...。Netwatch 会检查第二棵父 slice 是否实际存在，存在时同时生成规则，防止 exec shell 绕过应用策略。

cgroup namespace 不能省：xt_cgroup --path 相对命令调用者的 cgroup namespace 解析。所以防火墙命令使用 nsenter -t 1 -m -n -C -r。如果不加 -C，nftables 兼容后端可能报 RULE_APPEND failed (Invalid argument)。

四、设置代理

代理功能并不是向应用容器注入 HTTP_PROXY 环境变量。这种方式只对主动读取环境变量的程序有效，无法覆盖整个应用。Netwatch 使用透明重定向：在内核中按应用截获公网流量，再由本地适配器转换为用户配置的 HTTP 或 SOCKS5 上游协议。

应用发起连接目标仍是原始公网 IP 和端口。
NAT 匹配Bridge 按入口网桥，Host 按父 cgroup 匹配。
REDIRECTTCP，以及 SOCKS5 的 UDP，被送到该应用的动态本地端口。
恢复原目的地TCP 读 SO_ORIGINAL_DST，UDP 读 ancillary data/必要时查 conntrack。
上游转换执行 HTTP CONNECT、SOCKS5 CONNECT 或 SOCKS5 UDP ASSOCIATE。

4.1 透明重定向规则

目标NAT hookfilter hook匹配
BridgePREROUTINGFORWARD-i lzc-br-*
HostOUTPUTOUTPUT-m cgroup --path ...

私网目的地先 RETURN，保持直连。TCP 被 REDIRECT 后，filter chain 对仍留在公网的未支持协议执行 DROP，以“失败关闭”避免流量绕过代理。代理同样使用 NAT/filter A/B chain 完整切换。

4.2 每应用独立适配器

  • 每个 instance_id 保存自己的协议、IP 和端口，并使用独立的 appProxyAdapter 与动态内部端口。
  • HTTP 上游使用 CONNECT host:port 建立 TCP 隧道；SOCKS5 使用无认证 CONNECT，UDP 使用 UDP ASSOCIATE。
  • 对于 nftables 兼容层无法在 UDP ancillary data 中返回原始目的地的情况，适配器最多查询 4 次 nf_conntrack，每次间隔 3ms，从 original/reply tuple 恢复地址。
  • UDP 回包使用 IP_PKTINFO/IPV6_PKTINFO 选择反向 NAT 期望的源地址，使应用看到的仍是原始目的端。
  • 如果用户填写的代理 IP 是宿主机自身地址，Netwatch 先连 127.0.0.1/::1，失败再回退到所填 IP，避免 hairpin 访问问题。
HTTP 的边界：HTTP CONNECT 只能承载 TCP。因此 HTTP 模式下公网 UDP 和其他未支持 IP 协议会被阻断，不会悄悄直连。需要 UDP 时必须使用 SOCKS5 上游。

五、策略事务与功能互斥

POST /api/v1/network/app-policy 是字段级更新：未提交的限速、外网或代理字段保持不变。服务端先在同一个串行事务中读取当前策略并计算最终策略，避免两个并发请求都基于过期状态通过检查。

  1. 校验数值、代理配置、白名单、所有活动目标能力和互斥关系。
  2. 如果限速发生变化，先安装内核限速规则，并记住用于回滚的旧值。
  3. 如果代理发生变化，先安装 fail-closed guard，再启动新适配器并切换 NAT/filter；切换成功后才关闭旧适配器。
  4. 如果外网策略变化，重建 IPv4/IPv6 防火墙 chain。
  5. 所有内核动作成功后，才持久化限速、禁网和代理期望状态。

中间任一步失败都按相反顺序回滚已执行目标；即使最后写盘失败，也会恢复防火墙、代理适配器、内核限速和原持久化限速。回滚本身失败时，错误会与原始错误一起返回，不会被日志吞掉。

组合是否允许原因
禁用外网 + 限速否无公网可限速，同时存在只会造成误导状态。
禁用外网 + 代理否禁网优先。升级遗留配置会显示 paused，但新请求不允许创建这个组合。
Host/Mixed 限速 + 代理否两者都依赖宿主出口分类，当前不提供可证明正确的组合语义。
Bridge 限速 + 代理是网桥 tc 和透明代理 hook 可独立工作。

六、实际状态、自愈与清理

存储中的期望值不能证明内核规则还存在。Netwatch 把状态分为三层：

desired已持久化的用户期望：限速数值、禁网开关、每应用代理配置。
applied最近一次被 tc/iptables/适配器接受的状态，主要用于失败回滚。
in_sync最近一次核验中内核实际规则是否与 desired 一致。
  • 后台生命周期观察器约每 2 秒采集应用拓扑并 reconcile 策略；限速内核详细核验有自己的节流周期。
  • 网桥或 cgroup 重建、规则被外部删除、Netwatch 重启后，按 desired 恢复策略。
  • 取消限速会删除 Netwatch 保留的 qdisc/filter、Host cgroup attachment 与 map；不存在的规则按“已清理”处理。
  • 防火墙和代理更新会清理旧 A/B chain hook 与历史遗留直接规则，避免重复穿透。
  • 当 Docker 目标清单临时为空时，不会立即刷空一套正在生效的防火墙策略，而是等待下一轮完整发现。

前端应该使用 limit_in_sync、internet_in_sync、proxy_in_sync 和 diagnostic 判断现实状态，不能只看期望开关。

七、多实例应用的隔离

多实例应用中，不同用户运行的仍是同一 app_id，但必须使用不同 instance_id 保存和执行策略。Netwatch 优先使用懒猫 user-id 生成 <app_id>@user:<user>，必要时回退到 Compose project。

  • 多实例时只提交 app_id 的变更请求会被拒绝，前端必须一起提交当前行的 instance_id。
  • Bridge 实例按自己的网桥控制；Host 实例只在它们拥有可验证的独立父 cgroup 时开放变更型控制。
  • 如果两个 Host 用户实例共享父 cgroup，统计仍可按容器进行，但限速、禁网和代理能力会全部关闭，避免一个用户的策略误伤另一个用户。

八、当前边界与排障入口

场景当前边界首先检查
Host/Mixed 限速IPv4/IPv6 默认路由必须使用同一设备；暂不支持多 WAN、策略路由和运行中出口切换。network_policy.limit_in_sync、默认路由设备、优先级 49160/49161 的 filter。
Bridge 限速下载 TBF 会限制网桥发向容器的流量；上传对已列出私网 CIDR 旁路。root TBF 194:、上传 pref 49140–49144/49152、burst/MTU 和 gact pass。
禁用外网按 CIDR 定义私网，不是任意“本地地址”自动识别。internet_in_sync、活动 A/B chain、Host 命令是否加入 cgroup namespace。
HTTP 代理仅 TCP；公网 UDP 失败关闭。proxy_state/proxy_in_sync、该应用独立适配器和 NAT REDIRECT。
SOCKS5 代理只支持 IP 上游、无认证；UDP 需要 conntrack 与原目的地能力。上游可达性、nf_conntrack、UDP ASSOCIATE 会话。
一句话总结：限速是“识别流量后整形或丢包”，禁用外网是“私网例外 + 公网 DROP”，设置代理是“按应用透明 REDIRECT + 协议适配”；三者的可靠性来自同一套能力预检、事务回滚、实际状态核验和周期自愈。
